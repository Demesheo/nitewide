# Stripe Connect sandbox preparation

Nitewide-approved businesses with completed Nitewide onboarding can create and publish free events and manage guestlists without Stripe. Paid offerings can be prepared in drafts. Paid publication and checkout require the selected business payment profile to have fresh, provider-confirmed sandbox readiness and the server's payment integration to be fully configured. Browser returns, submitted flags, and Nitewide approval do not establish Stripe readiness.

## Confirmed integration

Business accounts use Accounts v2 merchant configuration, Stripe-hosted onboarding, and the full Stripe Dashboard. Stripe collects its processing fees and bears payment-loss responsibility on the connected account. Customer checkout uses Nitewide's interface with Stripe Elements, Checkout Sessions, and direct charges on the selected connected merchant. Named payment profiles support an organization default and an explicit event override; venue addresses do not identify the merchant. Unresolved checkout, payment-review and refund activity temporarily locks merchant selection. Completed transaction history does not permanently prevent changing the account for future payments.

The server is pinned to `stripe` SDK `22.6.0` and stable API version `2026-08-26.dahlia`, matching the confirmed Dashboard version. The official [SDK API version](https://raw.githubusercontent.com/stripe/stripe-node/v22.6.0/src/apiVersion.ts), [Accounts resource](https://raw.githubusercontent.com/stripe/stripe-node/v22.6.0/src/resources/V2/Core/Accounts.ts), and [Account Links resource](https://raw.githubusercontent.com/stripe/stripe-node/v22.6.0/src/resources/V2/Core/AccountLinks.ts) confirm support. Preview headers shown in some guides are not used.

Account creation requests `dashboard: full`, `configuration.merchant.capabilities.card_payments.requested: true`, and `defaults.responsibilities.fees_collector/losses_collector: stripe`. Retrieval explicitly includes `configuration.merchant`, `defaults`, and `requirements`: omitted include-dependent fields cannot grant readiness. On Dahlia, hosted onboarding links specify `use_case.account_onboarding.configurations: [merchant]`; links are single-use, returned only to authorized finance users, and never emailed or logged. Account Link timestamps are ISO strings. See [Accounts v2](https://docs.stripe.com/connect/accounts-v2) and the versioned SDK sources above.

Readiness requires an active local profile, test-mode v2 account, full Dashboard, Stripe fee/loss/requirement responsibility, applied merchant configuration, active card capability, completed current user requirements, and synchronization within five minutes. Closed or deauthorized accounts remain unavailable. Provider work runs outside database mutation locks; publication checks cached server evidence under locks. Migration `202610010007-stripe-accounts-v2.cjs` invalidates previous account-readiness caches so they must be refreshed through v2.

The full event editor automatically refreshes the selected merchant when creating a published event with active paid offerings or saving changes to one. An authorized preflight resolves the event override or organization default, releases its locks, and retrieves Stripe readiness. The final save rechecks permissions, event version, account selection and current readiness under locks. Users need not leave the editor for Payments → Check readiness after a long editing session. Drafts, free events, guestlist-only events and inactive paid tiers do not trigger this refresh. A restricted account or provider outage leaves the event unchanged and the entered draft available for retry; disabling or disconnecting an account still blocks paid publication. Event management does not grant finance-management permission, and existing orders retain their original merchant snapshots.

## Sandbox configuration and webhook destinations

The user has configured a local test secret securely. Credentials remain server-side, are not pasted into chat, and are not included in frontend bundles. Configure `STRIPE_MODE=test`, `STRIPE_SECRET_KEY=sk_test_…`, `STRIPE_PUBLISHABLE_KEY=pk_test_…`, and separate signing secrets for both destinations below. Payment enablement requires the account and payment webhook destinations to be configured. A secret key alone supports onboarding but does not enable paid publication or checkout. Live secret/publishable keys are rejected by this implementation.

Before enabling hosted Stripe, explicitly configure `CUSTOMER_APP_URL=https://<public-customer-host>` and `BUSINESS_APP_URL=https://<public-business-host>/app` on the API and worker environments. For the shared demo these are `https://nitewide-demo.onrender.com` and `https://nitewide-demo.onrender.com/app`. Production/hosted Stripe startup rejects missing, insecure, credential-bearing, localhost or private-address return URLs—even before webhooks or email delivery are configured. Local development can still use localhost. Callback URLs are server configuration, never inferred from a request's Host header. Updating a URL does not change an already-issued one-time onboarding link; issue a fresh link.

In Stripe Workbench, create two sandbox event destinations. Repeat these settings in production only after a separately authorized production implementation and validation; this code currently supports test mode only.

Already-paid orders open their passes without another confirmation; network, review, unknown or terminal states do not authorize payment. Existing order/provider snapshots and retry keys are not rewritten when wallet settings change.

### Background recovery and trusted state

Checkout and refund recovery run in the dedicated worker, not an API timer. One non-overlapping lane checks every 30 seconds, with at most one expired reservation and one pending refund reconciliation chain concurrently. It reuses durable provider keys and waits for in-flight work during bounded worker shutdown. Neither a local reservation timeout nor an unknown provider response releases stock or grants admission.

Capability synchronization records the provider request's start time under a short database lock. Older responses cannot replace newer readiness evidence; equal-timestamp responses can revoke but cannot restore permission. A slow response does not extend cache freshness. Closed/deauthorized profiles remain unavailable after stale updates.

Approved refund creation responses lost in transit are recoverable with the original `refund/<id>` provider key. Missing references older than 23 hours are held for manual provider reconciliation rather than recreated beyond Stripe's idempotency-retention window. Sandbox fulfillment suppresses real transactional email; ordinary mocked email tests remain in the normal suite.

Checkout Session creation parameters are saved privately with the order before the reservation commits: account/key, prices, fees, email, return URL, payment methods and expiry remain immutable across retries and configuration changes. A missing original snapshot, an unknown creation older than 23 hours, or insufficient time remaining to satisfy Stripe's 30-minute minimum creation expiry moves the order to audited review, retaining inventory. The initial session expiry is 35 minutes; an unknown creation therefore requires manual reconciliation after approximately five minutes. A known session ID can still be retrieved after that creation-replay window. Provider parameters and customer-email snapshots are excluded from customer order responses; client secrets are not persisted.

See [Stripe event destinations](https://docs.stripe.com/event-destinations) and [Accounts v2 integration](https://docs.stripe.com/connect/accounts-v2). The user created both sandbox Dashboard destinations and configured their distinct signing secrets locally and on Render. Both Render receivers are deployed; unsigned payloads are rejected. Actual provider delivery remains part of the pending end-to-end onboarding/purchase/refund check.

## Refunds and fees

On event cancellation, refund the entire customer payment, including Nitewide's application fee. The merchant bears any Stripe processing fee Stripe does not return. Refund execution requires merchant approval or an audited administrative override. Cancellation itself does not automatically issue a refund. Stripe's processing fee is distinct from Nitewide's application fee, which represents Nitewide's share only; calculations must not count Stripe costs twice. See [connected-account configuration](https://docs.stripe.com/connect/accounts-v2/connected-account-configuration).

Refunds initiated outside Nitewide, including in the merchant's Stripe Dashboard, are reconciled from independently retrieved account-scoped Charge/Refund evidence. A verified full customer refund and full application-fee return updates payment/order history and voids admissions atomically; audit records identify the external provider action without inventing a Nitewide approval. Partial, unsettled or application-fee-incomplete refunds withhold admission for review while preserving ticket history. External reviews without a local approved Refund record are not processed by the approved-refund sweep: they need a later subscribed provider event or manual reconciliation. Platform-only application-fee events and a general review-management UI remain future work.

### Payment account changes

Owners and finance-authorized managers can change an organization's default or an event's selected account once the affected Stripe activity is resolved. Pending checkout attempts, unverified/review payments, and pending or failed refunds block the change—even for ended events. Provider-confirmed expired checkouts, verified completed payments, and resolved refunds do not. Demo and free bookings alone do not establish a Stripe merchant and do not block selection.

Changing the organization default affects only events that inherit it; events with an explicit account keep that override. Every existing order, payment and refund retains its saved merchant identifier. A later refund still uses the original order's account, not the event's current selection. New paid checkouts use the new selection. Current published paid events still require a freshly verified ready merchant; ended or inactive events are not revalidated as if being published again.

Here, resolved means terminal, server-verified payment/checkout state and no outstanding refund record. It does not mean Stripe funds have reached a bank account. This workflow changes payment routing, not Stripe disconnection; the separate disconnection checks remain stricter. Dispute handling and complete live-money operations remain prerequisites before enabling production payments. Selection uses the same database authorization fence as checkout/refund writes, and the unresolved-refund lookup has a partial index for large histories.

## Business Payments workspace and individual commissions

Before a paid sandbox release, run the read-only [payment deployment preflight](API_DIAGNOSTICS.md#payment-deployment-preflight) against the running API with `--require-paid --expect-revision <SHA>`. It detects the missing deployed settings/merchant records that broke Render checkout and detects mismatched payment workers. It never repairs records, refreshes Stripe or makes payments. Provider key-pair identity and actual delivery to both webhook destinations remain explicitly unverified until separately demonstrated. `/health/ready` remains a database/draining probe, not a Stripe checkout check.

The dedicated **Payments** workspace separates business finances from **My commissions**. Owners and explicitly finance-authorized managers can see their organization's verified sandbox booking totals and manage merchant payment accounts. Commission earners can see only their own historical earnings, even when their effective rate is currently zero. No role grants access to another person's earnings. Organization settings no longer duplicate payment-account controls. Already-issued onboarding links returning to Organization still open the new Payments workspace.

`GET /business/organizations/:organizationId/payment-overview` aggregates all-time verified Stripe test bookings by currency. Customer payments include subsequently refunded bookings; remaining payments subtract cumulative provider-verified full and partial refunds. Pending/review counts are separate. Legacy mock payments are excluded. These figures are **not** the merchant's bank balance, Stripe processing-fee statement or payout history. Stripe manages those; the full Dashboard link requires Stripe sign-in and Stripe account/team authorization independently of Nitewide permissions.

`GET /account/commission-earnings` and `/account/commissions` use the authenticated user's identity, never a supplied recipient ID. Historical own earnings remain readable after removal from a business, without granting Business app access. Earned, held, unpaid, reserved and paid amounts are separate. Verified Stripe account credit is not a bank payout; bank payout tracking remains unavailable. Legacy mock earnings are never made payable automatically.

Agreed commission rules:

- Businesses fund separate referral-service payments from their authorized card or bank account, directly to the individual's full-Dashboard merchant account. Nitewide does not fund transfers or deduct commission from its application fee. Merchant-of-record ticket direct charges and Stripe-owned pricing remain unchanged; commission invoices have no application fee.
- Without completed **individual** Stripe onboarding and freshly verified recipient/payout eligibility, the person's effective commission is **locked at 0%**. Merchant/business onboarding cannot satisfy this rule.
- New booking calculation enforces the lock server-side. Nonzero commission invitations/edits are rejected while individual eligibility is unavailable. Zero-rate access invitations still work, including acceptance of legacy invitations. Copying existing assignments retains historical/configured terms but cannot activate unverified commission earnings.
- Saved historical rates and completed order commission snapshots are not rewritten. Read projections show the effective zero rate separately from configured historical terms; editing controls explain the lock.
- Individual setup uses a separate server-owned profile and Stripe-hosted onboarding. Synchronization independently verifies individual identity, full Dashboard, Stripe fee/loss responsibility, requirements and capabilities. Business setup cannot unlock a person's rate, and the temporary shared sandbox merchant never applies to individual accounts. A browser-supplied readiness object is never evidence.
- Commission-qualified paid offering subtotals exclude taxes, service fees and free items. The default floor is $10; organization defaults and nullable event overrides may only increase it. Combined cheaper paid items can qualify. Purchase rate/minimum/recipient/event terms are immutable snapshots; edits affect future attempts only.
- Owner or finance-authorized manager approves each event/recipient statement after the current event end plus 48 hours. Approved statements for one business, recipient and currency can be combined. Small unpaid amounts remain recorded indefinitely; they are not discarded by payment minimums.
- Verified refunds proportionally reduce unpaid earnings. A refund or dispute invalidates an outstanding unpaid commission invoice; provider-confirmed voiding releases its reservation and reapplies the adjustment. Unknown/processing provider outcomes retain their reservation for safe recovery, without allowing a second invoice. Only actually received commissions are retained costs borne by the business. Analytics uses net offering sales and retained commission cost, even after a full customer refund, without double-counting payment execution.
- Provider timeout retains the original payment reservation and retry key. Webhooks trigger independent invoice, PaymentIntent, charge and balance-transaction retrieval. An invoice marked paid manually, by credits or without verified charge evidence cannot settle a commission.
- The fee allowance is an estimate, not a promise of exact net proceeds. Processing fees are independently retrieved. Unknown attributable Invoicing fees leave the payment in fee review. An owner or finance-authorized manager may record those fees from the recipient's Stripe Dashboard with an evidence reference, reason and durable retry identity. This one-time audited record is labeled **merchant-reviewed**, never provider-verified. Net credits are split by evidence type. Only the received net amount settles the ledger; any unpaid residual returns to the statement for a fresh explicit payment approval, never an automatic extra debit. A Stripe credit does not establish a bank payout.

Invoice and charge notifications use the same connected-account snapshot destination as ticket payments. Include the commission/dispute events above. Payloads select provider objects but cannot establish receipt, fees or dispute outcome. Purchase dispute evidence holds only its booking, independently from refund-request holds; winning/closed inquiries release that hold, while lost disputes remain held for finance review rather than inventing a refund or clawing back paid commissions.

The implementation remains sandbox-only. Before live enablement, validate the referral-service use case with Stripe, actual processing/Invoicing fee evidence, shortfall resolution, chargeback recovery, tax reporting and genuine worker classification with appropriate advisers. An Employee or Manager app role does not automatically establish either employment or independent-contractor tax treatment; separate services and the actual control relationship matter.

## Organizer conversations and refund requests

Customers start a booking-linked conversation from **Contact organizer**. **Messages**, beside **Notifications** in Customer and Business, supports replies, unread state, pagination and explicit read acknowledgments. Existing notifications link to the thread. No organizer-contact email is queued or sent; message content is rendered as text, not HTML.

Customers may request cancellation/refund strictly before the event begins. Purchases are generally nonrefundable and organizer approval is discretionary. Sending a request does not revoke passes; only that booking's commission is held. Organizers may resolve timely requests after the event without a response deadline. Approval uses the original merchant's verified refund path; a failed response can retry the same persisted approval. Event-cancellation refunds, provider-originated refunds and audited admin exceptions retain their existing handling. Current authorized owners/managers see organizer conversations; promoters do not gain access to other customers' private messages, and removed/suspended organizers lose access.
